在人人都能 Vibe Coding 的时代，架构师的价值到底是什么？

实现变便宜之后，判断、证据与约束为何变得更贵。

文 / 大铭来自真实工作现场
NO.01DAMING.AI
EDITORIAL

先说结论：

EDITOR’S NOTE

VibeCoding没有消灭架构师。它只是让每个人都能更快地把想法变成系统——也能更快地把错误带进生产。

以前代码贵，一个错误想法要经过需求、排期、开发、测试，折腾几周才有机会进入生产。

现在不一样了。你跟CodingAgent聊半小时，页面有了，接口有了，测试也有了。再来几个Agent并行review，一晚上能出来好几份PR。

看起来，软件开发里最贵的部分突然便宜了。

但真正困难的那部分并没有消失：我们做的是不是对的事？系统上线以后，有什么证据证明它真的做对了？

数据库里的脏数据不会因为代码是AI写的就更容易恢复；权限越界不会因为PR有三个Agent点赞就伤害更小；模型向客户承诺“马上执行”却没有任何动作，客户也不会因为根因很智能就原谅你。

现在更常见的说法其实是：有了AI，我自己就能把产品做出来，还要技术干什么？

这句话之所以有吸引力，是因为它的前半句正在变成现实。一个懂业务的人，确实可以自己做出页面、接口，甚至把一个版本部署上线。

但能做出来，不等于做对了；能跑起来，也不等于可以放心交给真实用户。

这也是架构师在这个时代仍然有价值的原因。不是因为他比别人更会画图，也不是因为他掌握更多技术名词，而是当一个人带着AI高速实现时，持续确认：问题有没有定义对，系统有没有真的做对，我们又凭什么相信它做对了。

01 / FIELD DATA

三个月，73,490 条消息，我最关心的不是产量

从5月1日到7月26日，我把自己与Codex、Z-Code、ClaudeCode的AICoding记录按天做成了协作账本。

这87个自然日里，有79天存在可见协作记录，共计904个按天切分的顶层会话片段、73,490条可见消息。

最密集的一天是6月8日：37个顶层会话、2,333条消息，分布在11个不同工作目录。当天的工作面包括生产数据清理、两次版本发布、评价回填、海报引擎改造、计费修复、Agent调用网关、CLI、营销看板和排期工具等。

如果把“并行”定义得保守一点——不是会话开着就算，而是在同一个滚动30分钟窗口里确实出现过可见消息——峰值是9条顶层会话交错活跃，涉及4个工作目录。

这不等于9个Agent在每一秒都同时计算，更不等于我同时做了9个完整项目。但它至少说明了一种新的工作方式：一个人不再守着一条开发流水线往前走，而是在多个Agent、多个仓库和多个问题之间不断切换、校准和收口。

如果一定要显摆，我更愿意显摆这个，而不是“我和AI聊了七万多条消息”。消息多只能说明使用频繁；能让多条工作线不互相污染、不把讨论当完成、不把错误判断一起放大，才真正接近能力。

完整的数据来源和统计口径放在文末附录。这里面有大量代码生成、PRreview、测试、部署、生产诊断和产品讨论。过去一个小团队几个月才能完成的操作，现在一个人带着几个Agent就能同时推进。

但回头看，真正值钱的时刻几乎都不是“AI又完成了什么”，而是“原来的判断被什么证据推翻了”。

我把这些时刻归成三类。

第一类，系统实现得很快，但题目出错了。

第二类，所有局部步骤都成功，但整体并没有交付。

第三类，团队有一个合理解释，可真实因果链完全不是那回事。

这三类问题，其实都在说同一件事：团队做得越来越快，却没有人及时确认做得对不对。

这才是VibeCoding时代架构师的主战场。

02 / BUSINESS MODEL

第一种幻觉：能运行，就说明需求理解对了

我们做过一个月嫂工作台。

系统保存数据时报错，因为底层模型要求每条记录必须带门店。CodingAgent很快给出方案：没有门店就自动补一个默认门店。

多顺滑啊。字段不为空了，接口不报错了，测试也能过。

可业务上，这类服务者本来就是整个租户共享的资源。她的档期属于租户，不属于某个门店；一个家庭由哪个门店维护，是运营归属；某次服务算到哪个门店，是服务归属。

为了消灭一个非空错误，硬塞默认门店，相当于让数据库替业务做决定。

这就是VibeCoding最危险的地方：AI会把你说出来的问题当成题目，然后非常努力地把题做完。可真实世界不会替你检查题目是不是出错了。

同一个系统还出现过一个“今天可服务”的判断。算法找到一天空闲，就提示可以接单。

听起来没毛病，对吧？

但实际业务接的是连续二十多天的服务。一天空闲没有任何意义。真正的问题应该是：未来是否存在一段完整的连续档期？

如果没有业务模型，AI会把“找一个空闲日”做得很漂亮。页面有颜色，接口有字段，测试有断言，最后仍然是一坨逻辑正确、业务错误的东西。

所以，架构师第一件事不是选框架，而是维护一份关于真实世界的模型：谁属于谁，什么状态可以同时存在，什么数字有业务意义，哪些概念看起来相似但绝不能共用一个字段。

这份模型不一定是一张UML图。它可能只是一次追问：

月嫂到底属于门店，还是属于租户？

问题问对了，后面的代码才有价值。

03 / TECH CHOICES

技术选型，不是把名词堆进系统

业务出身的人开始VibeCoding，通常很快就能说清楚自己要什么页面、什么流程、什么结果。

真正容易卡住的，是另一类问题：这里要不要加缓存？任务是不是应该异步？要不要上消息队列？状态放数据库还是内存？要不要拆服务？失败以后允许重复执行吗？

这些听起来只是技术名词，背后其实是一整套取舍。

加一个缓存，不只是“系统会更快”，还意味着你要处理过期、失效、脏数据和两份真相。加一个消息队列，不只是“削峰填谷”，还意味着重复消费、顺序、重试、积压、监控和死信。拆一个微服务，也不只是多建一个仓库，而是把一次函数调用变成网络、鉴权、版本和故障边界。

AI可以在几分钟内把这些名词解释清楚，也可以给你生成一套Redis、Kafka、分布式锁和事件总线齐全的方案。

问题恰恰在这里：它太容易把“可能有用”写成“现在就需要”。

架构师的技术价值，不是比别人多背几个名词，而是知道每种技术在解决什么故障，又会引入什么新故障。他要把业务规模、一致性要求、失败代价、运维能力和未来变化放在一起，选出当前足够用、又不会堵死下一步的最小组合。

这部分判断确实来自长期积累。一个名词半小时可以听懂，但什么时候使用、什么时候不用、用了以后最先坏在哪里，往往是十几年踩坑留下来的东西。

不过，如果架构师只会用术语压住业务人员，那也没什么价值。真正的能力，是把这些取舍翻译成人能听懂的问题：数据允许旧一分钟吗？任务执行两次会不会多扣钱？服务挂掉以后消息是丢掉还是晚点再发？团队有没有人能维护这套基础设施？

问题回答清楚，技术组合才有答案。

04 / DELIVERY STATE

第二种幻觉：每一步都绿了，整体就交付了

6月，我们有一次发布很典型。

PR合并了，版本号更新了，tag推送了，目标测试也通过了。按很多团队的汇报口径，这已经叫“发布完成”。

结果生产一跑，数据库缺列。

代码已经进入新版本，数据库还活在旧版本。迁移文件不是没有，只是整个发布流程没有自动执行它，也没有可靠的迁移历史。

你说这次发布成功了吗？

Git说成功了，CI说成功了，包也生成了。但用户请求直接报错。

这三个月，我越来越在意一串看起来很啰嗦的词：

EDITOR’S NOTE

讨论、设计、实现、测试、本地提交、push、PR、合并、部署、生产验证。

很多人觉得这只是项目管理。不是。

这是系统事实的状态机。

本地测试通过，只能证明某个环境下某些断言成立；commit只能证明内容被记录；push只能证明远端分支收到；merge只能证明代码进入主干；tag也不等于服务已经部署；部署更不等于真实业务链路已经跑通。

AI很容易把这些状态压缩成一句“已完成”。因为它擅长总结，而总结天然会丢边界。

架构师必须反着来：不断把“完成”拆开，要求每个状态有自己的证据。

不是为了写更长的周报，而是为了回答一个最朴素的问题：

现在到底哪一层是真的？

05 / ROOT CAUSE

第三种幻觉：解释得通，就等于找到了根因

7月，生产发生过一次真实的Agent事故。

Agent调完一个工具，在续写轮里告诉客户：“我将立即开始进行详细审查。”然后什么也没发生。

没有任务，没有结果，只有一句信心十足的承诺。

第一反应很自然：模型又“只说不做”了。

于是修复方案也很自然：匹配“我将”“马上”“开始”等未来意图词，再配合“审查”“分析”“执行”等行动词。如果模型说了却没做，就提醒它再来一次。

AI特别适合做这个方案。中英文变体、否定词、完成态、正则、测试用例，它能给你补得非常完整。

但这时我只问了一个问题：

动作有没有发生，为什么要靠分析一句话来证明？

自然语言是模型说了什么，工具执行是系统做了什么。这两件事不是一个层面。

继续查模型调用记录，发现模型其实已经发出了toolcall。随后后端在真正dispatch之前触发异常，异常又被吞掉。已经流出的那句话被保留下来，最后看起来就像一次正常回复。

也就是说，不是模型只说不做，而是平台把模型已经发出的动作弄丢了。

当时工具审计表里没有记录，所以大家一度把“没有审计”当成“没有调用”的证据。可异常恰好发生在写审计之前。没有记录，不是调用不存在，而是执行链死得太早。

这件事最可怕的不是一个变量写错了。

最可怕的是，系统可以失败，却继续对用户表现得像成功；基础设施故障可以披着“模型偶尔不听话”的外衣存在数周。

一个合理解释，有时候只是系统用来掩盖真实故障的故事。

架构师的价值，就是不轻易接受这个故事。

06 / EVIDENCE

AI 会找答案，架构师要定义什么算证据

今天的CodingAgent很会找答案。

你让它查日志，它能列十个根因；你让它review，它能找到几十个风险；你让它修，它能快速生成实现和测试。

但软件系统不是知识竞赛。不是谁列出的可能性多，谁就赢。

真正困难的是定义证据标准。

“没有审计记录”能不能证明没有调用？不能，因为审计可能发生在故障之后。

“完成率100%”能不能证明压测通过？不能，因为实际吞吐可能没达到目标。

“四个进程都启动”能不能证明形成了并发压力？不能，它们可能根本没有同步起跑。

“CI全绿”能不能证明生产可用？不能，测试数据库和生产schema可能不是一个世界。

AI可以帮助搜集证据，但必须有人先决定：什么证据足以支持什么结论。

这不是AI智商不够，而是责任问题。

如果目标只是交一个PR，“大概率没问题”可能够用。可如果要决定系统能不能上线、事故是否真正修复、容量是否可以对客户承诺，那么“看起来合理”远远不够。

真正要为上线判断负责的人，必然会提高证据标准。

07 / GUARDRAILS

架构师不是人肉审核员

说到这里，很容易得出另一个错误结论：既然AI可能犯错，那就让架构师逐行review所有AI代码。

这条路也走不通。

AI一天能生成的代码，已经超过任何一个人逐行检查的能力。让架构师变成人肉质检员，只会把整个组织的速度卡在一个人的时间上。

真正有效的做法，是把架构判断变成机器可以执行的约束。

代码和数据库版本必须一起前进，就做迁移门禁；新增租户数据必须说明隔离方式，就做schema检查；工具失败不能伪装成正常回复，就定义失败契约并补生产形状的回归测试；压力请求可以被拒绝但不能拖垮其他用户，就把资源预算、主动拒绝和撤载恢复写进验收标准。

这才是Harness的价值。

提示词是在劝Agent记住规矩，Harness是让它绕不过规矩。

架构师真正的杠杆，不是自己看完所有代码，而是把一次经验变成以后每个Agent、每个开发者、每条流水线都会执行的机制。

08 / SUBTRACTION

好架构也包括：坚决不做

架构师还有一个经常被低估的价值：删除复杂度。

最近我们在一个自动入群系统里讨论上线边界。AI给出的设计里有两套activation_at：订单模块一套，发送模块一套。它们都要求运维人员手工填写“从什么时间开始生效”，目的是防止新版本上线后突然处理历史任务、给旧客户补发消息。

这个风险是真实的。系统第一次启动时会从最早保留的事件开始读取；旧任务一旦补齐身份，可能立刻满足15分钟兜底发送条件。

但我追问了一句：其实根本就不需要这个概念，对吗？

继续往下拆，真正不能删除的不是activation_at，而是一条业务约束：历史任务不能产生新的外部动作。

既然如此，更小的设计是：新环境初始化时把消费cursor放到当前最新位置；数据库里的旧任务一次性标记为跳过；以后重启只使用持久化cursor。这样既保住了“不能误发”的边界，又删掉了两套时间、人工配置以及订单和发送模块之间的重复判断。

这件事很能说明架构师怎样做减法：

01

先找到绝对不能破坏的约束，而不是先保住现有字段。

02

把“要解决的问题”和“当前解决办法”拆开，不把两者当成一回事。

03

检查系统已有的状态能不能表达这个约束，避免再造一份真相。

04

删除概念以后，沿着启动、重启、失败恢复和外部副作用重新走一遍，确认简单不是以埋雷为代价。

同样的事情，在这三个月里不只发生过一次。

我们曾经准备给一个Agent运行时维护idle / active / hitl-paused三套状态。AI很快可以补齐状态迁移、测试和文档。但真实需求只是同一会话不能同时跑两个turn，历史事实已经持久化，不需要再维护一套会漂移的三态真相。于是三态状态机被删掉，只保留单活并发保护。

另一次，团队差点把检索、路由和行业知识都塞进AgentKernel。最后反而决定保持Kernel纯粹，让知识和检索通过Skill接入。

架构不是“多设计几个层”。

架构是在关键位置增加确定性，也在其他位置拒绝不必要的确定性。

会加东西不稀奇。能在AI已经写得热火朝天时说“这层根本不该存在”，同时又能证明删掉以后不会破坏关键约束，才稀缺。

这确实有很强的UNIX味道：每个部分只承担清晰而有限的职责，通过简单接口组合，不在系统里制造多份互相同步的真相。

但重点不是崇拜“少”，而是追求整体上的可理解、可替换和可维护。代码少但暗藏假设，不叫简单；概念少、边界清楚、失败行为明确，才叫简单。

09 / DELIVERABLES

Vibe Coding 时代，架构师到底交付什么

如果让我把架构师的产物压缩成六样东西，我会选：

第一，真实的业务模型。不让数据库字段和局部报错替业务做决定。

第二，合适的技术组合。知道什么时候需要缓存、队列和新服务，也知道什么时候数据库、定时任务和一个简单进程就够了。

第三，跨层因果链。知道模型、运行时、工具、审计、数据库和用户反馈之间如何传递状态。

第四，不可破坏的不变量。系统失败不能伪装成成功；租户数据不能越界；部署不能跳过迁移；历史任务不能突然触达用户。

第五，可执行的证据门禁。不是提醒大家小心，而是让错误默认过不去。

第六，责任边界。知道什么可以让AI自主完成，什么必须由人确认，什么时候可以上线，什么时候应该停止继续投入。

这些东西一旦建立，AI就不再只是一个到处写代码的聪明实习生，而会变成真正的组织杠杆。

10 / THE WARNING

最先被淘汰的，可能正是某些架构师

我不认为“架构师”这个头衔天然安全。

只会画框图、念技术名词、离开代码和生产现场的人，可能比普通开发更早被AI替代。因为AI画图更快，术语更多，方案还更漂亮。

“我经验多，所以听我的”也不再有效。

经验必须被翻译成可验证的系统模型、反例、不变量和门禁。否则那不是架构能力，只是资历。

真正不会被轻易替代的，是那些能在开工前问对问题、在上线前要求证据，并且愿意为判断负责的人。他不一定叫架构师，也可能是CTO、资深工程师、产品负责人，甚至是那个在所有人准备庆祝时追问一句的人：

我们凭什么认为它已经成功？

∞ / CONCLUSION

最后

VibeCoding让实现变便宜了，但没有让“把事情做对”变容易。

当实现变得极其便宜，错误的业务模型、错误的因果解释和错误的完成声明，也会被更快地送进系统。
